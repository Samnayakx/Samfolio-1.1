    How to approach UX for agentic systems

    Feb 28, 2026

    7 min read · 11 min listen

    Useful memory is not total recall. It is the smallest set of context that improves the next decision.

    Agentic UX starts with memory design

    Most teams begin an agent interface with chat. But the quality of an agent is often decided one layer earlier: what enters its working context, what persists, and what gets discarded.

    The popular shorthand is that a larger context window creates a better memory. The research is less reassuring. In “Lost in the Middle,” model performance was strongest when relevant information appeared at the beginning or end of the context and dropped when the same information sat in the middle. In one condition, GPT-3.5 Turbo scored below its 56.1% closed-book baseline when the relevant document was buried among 20–30 documents.1

    Evidence ( 01 ) 56.1%

    The closed-book baseline that one long-context condition fell below when evidence was placed in the middle.

    Capacity is not the same as usable attention. A system can technically hold a fact and still fail to use it at the right moment.

    More context can create less clarity

    Another study added irrelevant details to grade-school math problems. Across the problems that models could originally solve, no more than 18% were solved consistently across every type of irrelevant context.2 The extra information did not add knowledge. It added competition for attention.

    For product teams, this changes the design question. Do not ask, “How much can the agent remember?” Ask, “What is the minimum context that reliably improves this decision?”

    Stored memory ≠ active context
Active context ≠ reliable recall
Reliable recall ≠ good judgment

    Four kinds of memory

    A useful agent separates memory by purpose instead of pouring everything into one transcript.

    Working memory

    The current goal, constraints, recent tool results, and unresolved decisions. It should be small, inspectable, and allowed to expire with the task.

    Episodic memory

    What happened in earlier sessions: decisions, outcomes, corrections, and exceptions. Store the event and its consequence, not an undifferentiated conversation log.

    Semantic memory

    Stable facts about the user, organization, and domain. Each item needs provenance, recency, and a way for the user to correct it.

    Procedural memory

    How work should be done: policies, workflows, permissions, and tool instructions. This belongs in governed rules, not in a model’s improvised recollection.

    A worked example of the four memories

    Illustrative: my own sketch, not a sourced fact.

    One task, four stores. Picture an agent helping someone plan a launch. Working memory holds this week's goal and the two open decisions. Episodic memory holds that last time a draft was rejected, and why. Semantic memory holds that the person prefers short briefs, with a source and a date. Procedural memory holds the rule that anything external needs sign-off.

    Why the split matters. If all of that sits in one transcript, a stale preference and a current constraint look identical to the model. Separated, each store can have its own lifespan, its own owner and its own correction path. That is the design work: deciding which store a fact belongs in before deciding how to retrieve it.

    Compression needs a contract

    “Summarize the conversation” is not a memory strategy. Compression should be structured around the decisions the agent will make later. A practical memory record can preserve:

    • Goal: what outcome the user is pursuing.
    • Entities: people, projects, files, and systems involved.
    • Constraints: deadlines, permissions, exclusions, and risk limits.
    • Decisions: what was chosen, by whom, and why.
    • Evidence: the source and timestamp behind each durable fact.
    • Open loops: unresolved questions and promised follow-ups.

    The raw material can remain in storage for audit or retrieval. The compressed record is what earns a place in active context.

    Retrieval is an interface decision

    Memory becomes UX when the system decides what to surface. If every layer sees everything, the agent becomes noisy. If each step sees only the evidence relevant to its decision, the agent can become faster and more legible.

    A later evaluation across eight long-context models reproduced the middle-position degradation. Randomly permuting documents and selecting a consensus answer improved accuracy by as much as 24% on the tested single-document QA tasks.3

    Evidence ( 02 ) +24%

    Maximum reported accuracy lift from document permutation and medoid voting in a long-context evaluation.

    The lesson is not that every product should run the same technique. It is that retrieval order, filtering, and verification are product behavior—not invisible implementation details.

    What I would do first on a real product

    My opinion, based on the tradeoffs above.

    Start with the smallest memory that helps. I would begin with working memory only and prove it helps on real tasks before adding anything that persists. Persistence is where provenance, staleness and deletion all become obligations. It is cheaper to add a store later than to explain to a user why the product remembered something it should not have.

    Build the correction path first. Before the agent saves a single durable fact, I would want the user able to see it and fix it. A memory nobody can inspect is a liability that grows with use. I would treat the controls as part of the memory feature itself, not a settings page added once complaints arrive.

    Design the memory controls

    Users need more than a generic “memory on” toggle. They need controls that match the system’s actual behavior:

    • Before saving: show what will persist and why it may help.
    • While using: reveal which memories influenced an answer or action.
    • After correcting: distinguish “fix this response” from “update this permanently.”
    • When stale: ask for reconfirmation instead of silently reusing an old fact.
    • On deletion: make the scope explicit and confirm that derived summaries are removed too.

    These controls turn memory from a vague promise into an inspectable product surface.

    Measure usefulness, not volume

    Token count and number of saved memories are capacity metrics. They do not tell you whether memory helps. A stronger evaluation tracks:

    • Retrieval precision: how often selected memories are relevant to the current task.
    • Retrieval recall: how often essential context is available when needed.
    • Correction persistence: whether a user’s fix survives future sessions.
    • Stale-memory rate: how often outdated context changes a recommendation.
    • Decision lift: whether memory improves task success against a no-memory baseline.

    Anthropic’s long-context experiments found that extracting relevant quotes into a scratchpad improved recall in every head-to-head comparison they reported, though with some latency cost.4 That is a measurable design tradeoff: more visible evidence and better accuracy in exchange for time.

    The interface is structured delegation

    Good agentic UX does not expose the full complexity of retrieval, ranking, and compression. It exposes the parts a person needs to judge the result: the goal the system inferred, the evidence it used, the durable facts it changed, and the action it proposes.

    If the experience feels simple, it should be because the system filtered deliberately—not because it hid uncertainty. The future of agentic UX is not an infinite conversation. It is structured delegation supported by selective, correctable memory.

    How I would explain this to a teammate

    My opinion, based on the tradeoffs above.

    Memory is a filter, not a bucket. The line I would use is that we are not building a bigger bucket, we are building a better filter. The question is never how much can it hold. It is what does this decision need, and who confirmed it. That reframing moves the conversation from model capacity to product behavior, which is where designers can actually help.

    Quiet is not the goal. A teammate may hear selective memory and picture a hidden one. I would push back: the agent should filter hard and still show its working, the inferred goal, the evidence, the change. Simple on the surface is fine. Simple because uncertainty was hidden is the version I would argue against.
